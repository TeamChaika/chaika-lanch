# Тестовая оплата QR Manager

В корзине доступна СБП через тестовый API QR Manager. Это проверка интеграции: деньги не списываются, доставка и отправка на кухню не создаются. В форме используйте вымышленные контакты. Телефон, имя и адрес остаются в форме браузера и не уходят в общую тестовую среду провайдера.

Официальная документация: https://docs.qrmanager.ru/docs/v2 (OpenAPI: https://docs.qrmanager.ru/static/merged_swagger-2.json).

## Настройка

В переменных существующего серверного приложения Timeweb:

- `QRM_MODE=sandbox`
- `QRM_API_KEY` — тестовый ключ из раздела «Тестирование» документации QRM.
- `APP_ORIGINS` — разрешённые адреса сайта, уже используемые админкой.
- `SESSION_SECRET` и S3 — существующая серверная конфигурация.

Ключ не должен попадать в Git или переменную `NEXT_PUBLIC_*`. Тестовый хост зафиксирован в коде: `https://app.devwapiserv.qrm.ooo`. Промышленный режим намеренно не реализован. `QRM_MODE=disabled` возвращает прежнее демонстрационное оформление.

## Сценарий

1. Добавить обеды, открыть оформление, заполнить тестовые контакты.
2. Нажать «Перейти к тестовой оплате».
3. Сервер повторно проверяет опубликованное меню, доступные даты и цену. Сумма и номенклатура передаются QRM в копейках; доставка — отдельная позиция.
4. Страница `/payment/<id>` показывает QR и ссылку, запрашивает статус. По документации стенд автоматически подтверждает платёж примерно за 15 секунд; сумма 50000 копеек даёт отмену. Приложение банка открывать не требуется.
5. Успех показывается только после ответа серверного SSE API с кодом 5 и совпадающей суммой. Коды 6/8 означают отмену/истечение, 0 означает тайм-аут ожидания SSE, а не истечение платежа.

Подарок за пять дат отображается в итогах. Его нулевая стоимость не включается в номенклатуру QRM, где минимальная цена позиции — 1 копейка. Параметры налогов и боевой фискализации не предполагаются из тестовых данных.

## Надёжность и хранение

- HttpOnly cookie идентифицирует браузер; чужой платёж по одному UUID прочитать нельзя.
- Попытка резервируется условной записью S3 до запроса к QRM. Повтор той же попытки возвращает сохранённый результат. Автоповтора POST к провайдеру нет: его API не документирует ключ идемпотентности.
- Если результат создания неизвестен или процесс прерван, попытка остаётся заблокированной для повторного POST. Она не объявляется оплаченной; при потере UUID провайдера автоматическое восстановление невозможно.
- Данные тестовых попыток шифруются и подписываются `iron-session` в `cms/payments/sandbox/*.sealed`. Это необходимо, поскольку существующий S3-бакет публичен. Персональные контакты вообще не сохраняются.
- Ограничение создания: 8 попыток за 10 минут на сеанс, 60 в минуту глобально. Проверки статуса — не чаще раза в 5 секунд на операцию; автоматический опрос страницы длится до 5 минут, далее доступна ручная проверка.
- Webhook содержит индивидуальный HMAC в URL. Даже верный callback служит лишь сигналом повторно проверить UUID и сумму через API QRM; статус из его тела не принимается на веру. URL webhook нельзя публиковать или записывать в прикладные логи.
- Меню, владелец и платёжные записи используют существующее хранилище, поэтому сохраняются при перевыкладке. Новый платный ресурс не нужен.
- Тестовые записи пока не удаляются автоматически; жизненный цикл S3 и хранение реальных заказов нужно определить до промышленного запуска.

## Проверки

`npx playwright test --config playwright.payments.config.ts` запускает локальный HTTP-стенд QRM и Next dev. Подмена хоста разрешена **только** в development и только на `127.0.0.1`; сборка production всегда использует настоящий тестовый API.

Проверяются интерфейс телефона/компьютера, успешный SSE после перезагрузки, серверные суммы/подарок, конкурирующие повторные запросы, отмена/истечение/тайм-аут, неверная сумма, callbacks, доступ другого браузера, шифрование записей, лимит и сохранение корзины при ошибке. Это контрактные тесты с локальным сервером, а не доказательство работоспособности внешнего стенда.

## Обнаруженный сбой внешнего стенда — 18 сентября 2026

`GET /users/check-api-key/` принял опубликованный тестовый ключ и вернул «Тестовая компания», «Терминал 24». `POST /operations/qr-code/` с суммой 65000, в том числе с полной номенклатурой, вернул HTTP 400:

```text
Cannot assign "<Qrt: Терминал 24>": the current database router prevents this relation.
```

Это блокирует получение настоящего тестового QR. Пользователь видит ошибку сервиса, корзина сохраняется. Текст для обращения в поддержку QRM: «На тестовом хосте из документации v2 проверка публичного API-ключа проходит, но POST /operations/qr-code/ возвращает указанную ошибку database router для Терминала 24. Просим восстановить тестовое создание QR». Обращение автоматически не отправляется.

Для реального запуска отдельно нужны договор/терминал и боевой доступ, согласованная фискализация, приём и обработка заказов рестораном, доставка и интеграция с iiko. Успешная тестовая оплата их не включает.
