# Оплата QR Manager

Официальный контракт: https://docs.qrmanager.ru/docs/v2 и https://docs.qrmanager.ru/static/merged_swagger-2.json.

## Конфигурация

Серверное приложение Timeweb использует следующие переменные:

- `QRM_MODE=live` — реальные заказы; `sandbox` — тест; `disabled` — демонстрационное оформление.
- `QRM_LIVE_API_KEY` — боевой ключ терминала. `QRM_API_BASE_URL` — HTTPS origin боевого API, выданный QR Manager. Не угадывайте адрес по адресу тестового сервера.
- `QRM_API_KEY` — отдельный тестовый ключ из раздела «Тестирование». Сохраните его при переключении режима, чтобы проверять старые тестовые операции.
- `APP_ORIGINS` — адреса сайта через запятую; проверяются при оформлении и WebSocket Upgrade.
- `SESSION_SECRET` и S3 — существующая конфигурация. Не меняйте SESSION_SECRET: он нужен для расшифровки заказов и проверки webhook.

Ключи хранятся только в серверном окружении. Локальный файл `.env.qrm-live.local` исключён из Git; его `QRM_API_KEY` переносится в серверную **QRM_LIVE_API_KEY**, а не в тестовый ключ. API не принимает адрес провайдера от посетителя. Разрешены официальные домены QRM; иной выданный адрес требует проверки и изменения серверного списка.

Перед созданием боевого QR выполняется `GET /users/check-api-key/`: терминал должен принимать B2C, а компания не должна быть тестовой. Если API сообщает прошедшую дату окончания подписки, создание останавливается до обращения к платёжному POST. После продления терминала следующая проверка использует новую дату; менять ключ или перезапускать сайт для этого не нужно. Валидный API-ключ сам по себе не подтверждает активную подписку. Сумма передаётся в копейках. Номенклатура отправляется при включённой фискализации или номенклатуре терминала; доставка — отдельная позиция. Email передаётся QRM только при включённой фискализации, `payment_method=1` — полная предоплата. Ставка НДС не задаётся приложением: используется настройка терминала. Настройки кассы, налогов и последующего зачёта предоплаты должны соответствовать процессу продавца. Изменение статуса заказа на «Выполнен» само по себе не вызывает кассовый чек или iiko.

## Полный цикл

1. Сервер проверяет актуальное меню, даты, количество, цену и контакты. До обращения к QRM сохраняются зашифрованный заказ, индекс админки и очередь сверки.
2. POST `/operations/qr-code/` выполняется ровно один раз для зарезервированной попытки. При повторе запроса сервер возвращает сохранённый результат. В боевом режиме один браузер не может создать ещё один незавершённый платёж через другую вкладку.
3. Покупатель видит QR, сумму и «Ожидаем оплату». Сайт подключает WebSocket `/api/payments/ws?id=<uuid>` с HttpOnly cookie. Чужой origin, браузер или заказ не допускаются; входящие команды WS запрещены.
4. QRM отправляет webhook на URL, переданный при создании. В URL есть отдельный HMAC для заказа и среды. Callback — только сигнал: сервер перепроверяет UUID и сумму через GET `/api/v2/sse-operations/<uuid>/qr-status/`. В актуальной v2 этот GET возвращает SSE; старый WebSocket QRM не имеет опубликованного контракта. WebSocket в этой интеграции работает между покупателем и нашим сервером.
5. Только код 5 и точное совпадение суммы дают «Оплачен». Коды 6/8 — отмена/истечение; код 0 — окончание ожидания SSE. Повторные callbacks идемпотентны. Запоздалый pending/cancel не отменяет подтверждённую оплату.
6. WebSocket передаёт результат покупателю. Если соединение отсутствует, страница делает GET-проверки. Есть ручная кнопка; возвращение в открытую вкладку также проверяет результат.
7. Независимый серверный worker сверяет устойчивую очередь каждые 15 секунд, порциями до 8 записей. Он продолжает работу без вкладки покупателя и восстанавливает очередь после перезапуска приложения. Отменённые/истёкшие операции проверяются ещё сутки для обнаружения позднего подтверждения. Подтверждённые оплаты сохраняются бессрочно, но убираются из очереди.
8. В `/admin/orders` владелец видит контакты, адрес, дни, позиции, сумму, подарок и результат оплаты. Только оплаченный заказ можно принять в работу, затем отметить выполненным. Заказы фильтруются по дате **оформления**, отдельно для live/sandbox. Список обновляется каждые 30 секунд; «Показать ещё» загружает следующие 30 записей.

## Неопределённый результат

Автоповтора POST к QRM нет: провайдер не документирует ключ идемпотентности. Если ответ создания потерялся, корректный webhook может восстановить UUID и подтвердить его через GET. Если одновременно нет ответа с UUID и webhook, попытка остаётся «Требует проверки»; нужна сверка владельцем с кабинетом QRM. Не следует создавать второй платёж вслепую. Неверная сумма никогда не помечается оплаченной.

## Хранение и эксплуатация

- Заказы с контактами шифруются и подписываются `iron-session` в `cms/payments/live/*.sealed`; тестовые — в отдельном sandbox-разделе без контактов. Публичный S3 не содержит открытых персональных данных в индексах: там только случайные UUID.
- Условные записи S3 защищают от гонок. Секреты, контакты и URL с webhook-токеном не пишутся в прикладные логи. Причина отказа провайдера сохраняется только внутри зашифрованного заказа для владельца, с удалением ключа и URL.
- Лимиты: 8 созданий за 10 минут на браузер, 60 в минуту глобально; обычная GET-сверка не чаще 5 секунд; до 3 WS на cookie и 200 соединений на процесс. Webhook может выполнить внеочередную сверку.
- Runtime: `node server/gateway.mjs` слушает публичный PORT и проксирует HTTP в Next standalone на loopback:3001. Gateway выполняет WS Upgrade и фоновую сверку; случайный внутренний токен передаётся только дочернему Next. `/api/internal/payments/reconcile` без токена недоступен.
- Dockerfile явно включает gateway и пакет `ws`; локальный `next dev` без gateway всё равно поддерживает GET fallback. Успешный HTTP-деплой не доказывает WSS — проверяйте upgrade по публичному адресу Timeweb.
- Корзина очищается только после подтверждения; записи не удаляются при перевыкладке. Новые платные сервисы не требуются. Доставка, возвраты, уведомления менеджеру и iiko не автоматизированы этой интеграцией; команда работает со списком заказов.

## Проверка

- `npx playwright test --config playwright.payments.config.ts` — совместимость с тестовой средой, цены, суммы, SSE, поддельные callbacks, ошибки и браузерные сценарии.
- `npx playwright test --config playwright.live-payments.config.ts` — локальный имитатор QRM, реальный WebSocket gateway, webhook+GET, шифрование контактов, потерянный ответ, ранний callback, worker без браузера, изоляция клиентов, админка, телефоны и компьютеры.
- `QRM_TEST_ORIGIN` действует только в development и только для 127.0.0.1. Боевой Docker не допускает подмену хоста этим параметром. `MENU_LOCAL_NAMESPACE` изолирует локальные данные тестов.

Эти тесты не переводят деньги и не доказывают реальное зачисление банком. Для приёмки боевого терминала покупатель оплачивает один настоящий заказ; затем сопоставляются кабинет QRM, статус сайта, сумма и чек.
